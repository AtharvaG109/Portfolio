## Problem

The goal was to turn a networking prototype into a credible public systems project. The useful release needed a validated traffic path, strict HTTP parsing, platform-specific event-loop correctness, repeatable test gates, and honest release boundaries for the parts that were not yet production-ready.

## Architecture

- The server uses a custom non-blocking event loop based on `kqueue`/`epoll`, with platform-specific fixes for macOS filter registration and Linux fd delivery.
- It includes BoringSSL integration work for TLS handling, while the documented validated path remains cleartext HTTP/1.1 forwarding.
- It parses HTTP/2 frame behavior and HPACK table paths under tests, with complete stream-state handling and HPACK Huffman decoding still documented as release blockers.
- The public path forwards HTTP/1.1 client traffic to HTTP/1.1 upstreams with strict parser behavior and clear failures for unsupported request bodies.

## Key Technical Challenges

- **kqueue edge-triggered correctness**: Discovered that macOS kqueue silently drops filter registrations when batched with a failing delete of a non-existent filter. Solved by applying each filter change individually and tracking registered state per fd.
- **Linux epoll delivery**: Fixed event payload handling so listener and client events deliver the real file descriptor instead of a nullable user-data pointer.
- **TLS application data**: The codebase has TLS-path coverage, but the README keeps TLS termination as a release blocker until it is validated end to end against untrusted traffic.
- **Connection pool reliability**: Pool behavior is tested as infrastructure, while pooled upstream reuse remains outside the validated production path.
- **HTTP/2 boundary**: Frame and HPACK behavior are covered as protocol work, but complete HTTP/2 stream-state support is not claimed as production-ready.
- **Honest status**: The README explicitly says the current validated path is cleartext HTTP/1.1 forwarding, which keeps the project credible.

## Proof Signals

- The local gate covers Makefile tests, CMake tests, formatting, and defect-oriented static analysis.
- Regression tests cover HTTP/1.1 parsing, HTTP/2 frame behavior, HPACK paths, event-loop delivery, and connection-pool behavior.
- CI runs the release gate on GitHub so the public repo is not just a local-only build.
- Contributor verification kept the public history aligned with the one-author project claim.

## Deliberately Avoided

- No Kubernetes, service mesh, or distributed control plane; the project is the proxy implementation itself.
- No production-ready claim before TLS termination, HPACK Huffman coding, full HTTP/2 stream-state handling, and pooled upstream reuse are validated end to end.
- No broad benchmark claim without correctness coverage around protocol behavior.
- No overbroad lint profile that drowns real defects in style noise.

## Result

uProxy is a C++20 reverse-proxy foundation with a validated cleartext HTTP/1.1 forwarding path, tracked public headers, repeatable Makefile and CMake gates, formatting checks, CI, and protocol-focused regression coverage. It is presented as a strong systems project without hiding the remaining blockers for untrusted production traffic.
